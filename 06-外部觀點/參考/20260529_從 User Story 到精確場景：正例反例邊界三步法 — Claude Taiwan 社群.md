# 從 User Story 到精確場景：正例反例邊界三步法

> [!info]
> 原文：[Claude Taiwan 社群貼文](https://www.facebook.com/groups/1224997379198346/posts/1307950370903046/)
> **一句話：** User Story 只說「要做什麼」，但不說「什麼情況算做到了」——用「正例→反例→邊界」三步法把模糊需求拆成 Claude Code 能精確執行的 GIVEN-WHEN-THEN 場景，讓 AI 自動測試並把紅燈修完再回報。

---

## 核心問題

> 「AI 很會寫驗證輸入輸出正確的測試，但不怎麼會寫驗證商業邏輯的測試。」
> — Maple Kuo

User Story 的格式（角色 + 目標 + 價值）是對的，但它本來就不負責回答「什麼情況下算做到了」。

### 以課程平台為例

User Story：
> 作為學員，我希望完成所有課程單元後自動獲得結業證書。

丟給 Claude Code，它會做出一個「完成課程就發證書」的功能。但：

- 「完成」的定義是什麼？看完影片？通過測驗？
- 看完 9 個單元、跳過第 3 個，算「所有」嗎？
- 影片只看了 30 秒就算完成？
- 測驗考了 20 分算完成？

**User Story 是起點，不是終點。**

---

## 正例 → 反例 → 邊界 三步法

### 第一步：正例（Happy Path）

```
Scenario: 完成所有單元後頒發證書
  假設：已開設一門包含 3 個單元的課程，每單元含影片和測驗
        且學員已觀看所有影片超過 80%
        且學員所有測驗皆已達 60 分以上
  當：學員完成最後一個單元的測驗
  那麼：應自動頒發結業證書
```

寫完正例，隱含規則自然浮現：**影片 > 80%、測驗 ≥ 60 分**。

> [!tip] GIVEN-WHEN-THEN 結構說明
> - **假設（GIVEN）**：所有已成立的前提條件（用過去式）
> - **當（WHEN）**：只放一個觸發動作
> - **那麼（THEN）**：用「應」字描述預期結果
> - 一個場景只測一件事

### 第二步：反例（每個條件寫一個「剛好不符合」的版本）

```
Scenario: 影片觀看不足不頒發證書
  假設：已開設一門包含 3 個單元的課程
        且學員已觀看 2 個單元的影片超過 80%
        但第 3 單元影片僅觀看了 40%
        且學員所有測驗皆已達 60 分以上
  當：學員完成最後一個單元的測驗
  那麼：不應頒發證書
        且應顯示「尚有未完成的單元」

Scenario: 測驗未達標不頒發證書
  假設：已開設一門包含 3 個單元的課程
        且學員已觀看所有影片超過 80%
        但第 2 單元測驗僅取得 45 分
  當：學員完成最後一個單元的測驗
  那麼：不應頒發證書
        且應顯示「第 2 單元測驗未通過」
```

> [!tip] WHEN 固定不動
> 三個場景的「當」都是同一個觸發動作，差別只在「假設」的前提條件——這就是 GIVEN-WHEN-THEN 的威力。

### 第三步：邊界（剛好在及格線上）

```
Scenario: 影片剛好觀看達 80%
  假設：已開設一門包含 1 個單元的課程，影片長度為 10 分鐘
        且學員已觀看該影片剛好 8 分 00 秒
        且學員測驗已達 60 分以上
  當：學員完成該單元的測驗
  那麼：應頒發結業證書

Scenario: 測驗剛好 60 分
  假設：已開設一門包含 1 個單元的課程
        且學員已觀看影片超過 80%
        且學員測驗取得 60 分
  當：學員完成該單元的測驗
  那麼：應頒發結業證書
```

## 把場景丟給 Claude Code 的完整 Prompt

```
請讀取以下驗收場景，根據場景中的業務規則實作功能，
並為每條 GIVEN-WHEN-THEN 產生對應的 E2E 測試。
跑測試，紅燈就修正後重跑，全部綠燈再回報測試結果。
如果場景沒有覆蓋到的情境，不要自己猜，標記為 TODO 回報我。

（貼上場景）
```

Claude Code 回報：

```
🧪 驗收測試結果
✅ 完成所有單元後頒發證書
✅ 影片觀看不足不頒發證書
✅ 測驗未達標不頒發證書
✅ 影片剛好觀看達 80%
✅ 測驗剛好 60 分
```

**你不需要手動 Test Run——Claude Code 在回報前就已經把紅燈修完了。你只需要判斷：這些結果是不是你要的。**

## A vs B：場景要自己先寫還是讓 AI 先展開？

| 做法 | 優點 | 缺點 |
|---|---|---|
| **A：自己先寫 3–5 個，再請 AI 擴展** | 定調關鍵場景與語言風格；強迫深入理解業務規則 | 門檻較高；AI 容易被你的觀點限制 |
| **B：直接請 AI 展開，再人工審核** | 啟動成本低；AI 可能想到你沒想到的角度 | AI 容易一本正經講幹話，列 30 個有 20 個不是關鍵場景 |

> [!warning]
> 「AI 擅長沿著人給的模式擴展，但它不知道哪些場景對你的業務是關鍵的——這一步仍然是人的判斷。」

## 單角色盲點

即使用了 SbE（實例化需求），一個人想場景仍有盲點——你會沿著自己的經驗去想，想不到的就是想不到。

例如：

```
Scenario: 課程下架後仍頒發已完成學員的證書
  假設：學員已完成所有單元，符合頒發資格
        且該課程已被下架
  當：系統執行每日結業資格檢查
  那麼：應頒發結業證書
```

這個場景從「學員視角」看不出來，只有「營運端」才知道課程會下架。**不同角色一起審場景，遺漏才能最小化。**
