# /refactor-note — Refactor Note

重構一篇筆記、一個資料夾、或任何清單結構時，用「**注意力上限**」原則決定要不要分組，但**動手前一律先寫計劃書給用戶核准**。

## 執行流程 — Workflow

**不要跳過 plan 直接動手改**。兩階段：

1. **先寫 refactor 結構計劃書**：寫成一份 `.md` 檔（例：`REFACTOR-PLAN.md` 放在被重構的資料夾裡，或 `05-notes/refactor-plans/yyyymmdd-xxx.md`），**commit + push**，送用戶審。計劃書本身也要照 ai-101 的自動 commit 規則落 git。
2. **用戶核准後才執行**：用戶明說「照這份做」「OK」「GO」或等效答覆，才動 `git mv` / Write / Edit。核准前連試水溫改一個檔都不行。execute 另外切 commit，跟 plan commit 分開。

計劃書寫到使用者可以**只讀計劃書**就看懂會變成怎樣，不用自己再想一次。

> **為什麼要先 plan**：重構常跨多檔，一旦開始動 `git mv` 跟同步相對連結，中途改方向成本高。寫計劃書時被用戶 push back 的成本遠低於做到一半才發現方向錯。
>
> **為什麼 plan 要 commit**：萬一用戶離線、session 中斷、或要跨機器審，plan 必須在 repo 裡找得到。chat 裡的 plan 消失得太快。

## 計劃書格式 — Plan Template

每份 refactor 計劃書至少含以下 5 塊：

### 1. 現況盤點 — Before

- 這一層目前有幾個項目？列出來
- 哪些超過了 7 / 10 的門檻？
- 自然的同質群組有哪些？

### 2. 建議結構 — After

- 新的層級樹長什麼樣（資料夾 / 檔案 / 章節名稱）
- 每個新資料夾／分組的「主題」用一句話描述
- 新結構各層級都 ≤ 10，標出來給用戶檢查

### 3. 具體搬動 — Moves

- 哪些檔案 / 項目 / 章節 搬到哪，一條一行列成表或清單
- 標出跨資料夾的 `git mv` 跟相對連結要同步修的檔案
- 若有改名（kebab-case、順序前綴），同步列出

### 4. 風險 — Risks

- 哪些地方可能壞掉：相對連結、索引頁、外部參考、CI 腳本、Obsidian 內部連結
- 不確定的分類：點名給用戶拍板
- 可能要後續補的（如：之後要補 README 或更新 CLAUDE.md 的目錄說明）

### 5. 執行順序 — Order

- 哪個動作先做（通常是 `git mv`），哪個後做（更新索引）
- 分幾個 commit，每個 commit 收什麼。**plan 本身一個 commit, execute 另外切 commit**（通常執行階段還會再切成 2-3 個：搬檔 → 更新連結 → 更新索引）
- 讓用戶看得出中斷點在哪，萬一要暫停不會卡在半完成狀態
- 計劃書寫完先 commit + push, 等用戶核准後, 執行階段的 commit 再陸續上

## 核心原則 — The Rule

人的注意力大約落在 **3～7 個項目**，**10 是上限**（超過就記不住、掃不完）。

所以任何**單一層級**的項目數量都遵守：

- **第一層資料夾數量** ≤ 10
- **一個資料夾裡的東西總數** ≤ 10
- **一篇筆記裡同一層的小標 / 清單項** ≤ 10

> **7 是比較合理的目標數字，10 是硬上限。**

## 怎麼套用 — How to Apply

寫計劃書時走這條流程：

1. 數一數目標層級目前有幾個項目
2. **超過 10** → 把**同質性**的項目挑出來，建一個資料夾（或一個上層分類）收進去
3. 分組後回頭檢查：新的一層是否又超過 10？超過就再分
4. 分組的依據是「同質性」——同一主題、同一用途、同一類型才放一起，不是為了湊數硬塞

## 判斷要點

- **寧可 7 不要 10**：接近上限就該考慮分組，不必等真的爆掉
- **只分同質的**：找不到自然的同質群組，就別硬分——勉強的分類比不分還糟
- **每層都算**：分組解決了這一層，但別讓新資料夾內部又爆掉，逐層往下檢查
- **同質性不只看主題**：**時間**也是一種同質性。當項目彼此主題各異、但都是「陸續累積的同類產出」時，用**日期**分組／排序比硬塞主題分類更自然
  - 例：`06-external/` 的外部觀點，各篇主題天差地遠，但共通點是「陸續收錄」，所以用日期（`yyyymmdd_` 前綴）當同質性維度來排序與命名

## 時間分組的維護節奏 — Monthly Archiving

日期格式的筆記（如 `06-external/` 的 `yyyymmdd_` 前綴）會**持續累積**，靠單層排序遲早破 10。用固定節奏按月歸檔：

- **觸發時機**：進入下個月後，上個月就「封月」
- **做法**：所有過去月份收進 **`archive/yyyymm/`**（如 `archive/202605/`）。若原本有 `reference/` 這類重要性分層，在月份資料夾**內保留**：`archive/202605/reference/`。
- **效果**：頂層只留「當月累積中」的筆記 + 長駐資料夾（`reference/`、`archive/`）；過去每月各收一個資料夾，兩個軸（時間、重要性）都保留。

> 這是「時間同質性」的排程版——不必等頂層爆掉才手動分，按月自動收斂。`06-external/` 已採此結構。

## 適用對象

不只筆記——資料夾樹、README 章節、清單、選單、設定分頁，任何「人要一眼掃過」的結構都適用。
